已批准方案（D-DS-20261019）

在 Tojima 既有 token 上演進出自有設計系統；向 Tachiko Sheet 只借「方法」，不借色彩、元件或程式碼

  • 單一來源在程式碼。CSS custom properties 三層：primitive → semantic → 店家品牌層。完全落在 ADR-0006（原生 CSS＋CSS Modules、React Aria 只用於複雜元件）之內，不新增依賴。
  • 一套 token，四種表面模式。顧客 Guest／店員 Floor／廚房 KDS（暗色、大字）／後台 Office（高密度表格）以 data-surface 切換，涵蓋 MOD-05 現在與 MOD-02/03/07 未來。
  • 店家品牌受閘門保護。店家只能給一個顏色；系統自動推導填色上文字色、品牌文字色與焦點色。閘門檢查的每一組品牌配對，在 2,000 個隨機色下都達 WCAG AA（實際渲染位置以 DS-2 的元件測試再驗證）。狀態色、價格、焦點、DEMO／法定標示為受保護角色。
  • 從 Sheet 借方法：語意角色契約、受保護角色、可執行的對比度門檻、3px 焦點環、forced-colors、「狀態真實性」（未知／同步中／失敗分開顯示）。不借：紫色調色盤、32px 桌面密度、試算表元件、程式碼本身（Linear 文件 05 規定不混用 Tachiko 的 IP 與商標）。

D 也可以看作「只繼承方法」的選擇性繼承。本報告把 C 定義為搬入 Sheet 的資產（token 值、CSS、元件），D 則以 Tojima 自己已驗收畫面使用的綠色 token 為基底，只重新實作被驗證過的機制。差別在於有沒有搬資產：不搬，就避開 IP 歸屬未定的問題，也不會出現兩種視覺語言並存。

D 的風險（誠實列出）

  • 沒有專職設計師與 Figma 權威稿；視覺品質靠原型＋實機審查，需 Owner 或東島さん參與實機驗收。
  • 品牌閘門會調整約 15.6% 的任意店家色（2,000 個隨機色中 311 個需加深），店家後台必須預覽調整結果。
  • 後台高密度元件僅有樣本；MOD-02/03 需求確定前不擴充，避免投機性元件。
  • 系統字型在 Android 與 iOS 字形差異較大，需實機截圖比對（對應 P-84 GAP 7g）。

被否決方案的保留價值

  • A：Sheet 的試算表密度（28/32px 列高、tabular 數字、安靜外框）可作為 MOD-03 財務表格的參考，以概念重寫。
  • B：「重新設計」留給 MOD-07 會員 App 的品牌體驗；D 的品牌層是它的地基。
  • C：若 Owner 日後書面授權 Sheet 程式碼再利用，contrast checker 可直接比對兩邊實作。

03 · 設計驗證

Mobile Order 可操作原型

以 DEMO 店 シロナガスクジラ 的 9 個可點餐品項與「ごはんの量」必選選項建構。全部顏色、字級與尺寸都取自上方提案的 token。可切換語言、店家品牌色與網路狀態；點商品 → 選項 → 共用購物車 → 確認金額 → 訂單狀態。此原型不連接任何 API，也不進行付款。

店家品牌色（除 Tojima 既定外皆為假想色，非店家核准）
輸入任意顏色測試閘門
網路狀態
C06 例外狀態
跳至畫面
  1. UX-1菜單優先。首屏即是分類與品項；共用購物車改為底部常駐列（件數＋含稅合計＋同步狀態），點開為 sheet。
  2. UX-2文字優先的品項列。沒有授權照片也成立（DEMO-01 禁用第三方照片）；店家提供照片時以 72px 縮圖插槽加入，不改版面。
  3. UX-3選項在 sheet 內完成。必選群組未選時按鈕仍可按，按下後以受保護的錯誤色標示群組並移動焦點，而非灰掉按鈕讓人猜原因。
  4. UX-4調理狀態與付款狀態分兩條軌道。對應規格「訂單狀態與付款狀態分開顯示」。刷卡先顯示「等待付款」，要明確完成付款（原型以模擬按鈕代替 Stripe）才變成「已付款」；「C06 例外狀態」可切換不明、已付款待店家確認、已取消，不猜測。
  5. UX-5連線不穩時誠實降級。顯示最後同步時間、停用送單並說明原因；購物車內容保留。
  6. UX-6顧客看到的是店家，不是平台。頂部為店名與桌號，「Powered by Tojima」只在頁尾；為 MOD-07 白標預留。
  7. UX-7DEMO／參考價格標示為全域受保護橫幅，不再每個品項重複；購物車與確認 sheet 內也重複一行，避免被 sheet 遮住。不可被品牌色覆蓋。

06 · 後續實施方向（已批准，DS-1 規劃中）

五個小包，每包都有第一個真實需求

遵守 ADR-0006「第一個真實需求才引入」與「不為統一而重寫已驗收畫面」。實作由 Codex 執行，每包以全新唯讀 Codex 審查同一 SHA，並附實機截圖。

DS-1
Token 基礎＋無障礙修正新增 web/src/shared/tokens.css，把舊變數（--ink、--muted…）對應到語意 token；修正對比與 9–11px 字級；把對比門檻加入 pnpm check（Vitest）。外觀延續現在的綠色。第一個需求：P-84 無障礙 GAP。
DS-2
顧客端 IA：菜單優先＋sheet＋常駐購物車列＋雙軌狀態改動 App.tsx 的版面，不改 API 與 cart CAS 邏輯。底部 sheet 是第一個需要焦點收容的複雜元件，依 ADR-0006 於此包引入 React Aria（Dialog/Modal）。需 WebKit＋實機驗收（P-84 7g）。
DS-3
Floor / KDS 表面暗色 KDS、大字、輪詢失敗與資料過期提示（ADR-0006 已知缺口）。不含店家品牌。
DS-4
店家品牌層（需 Q2 批准）伺服器端儲存單一店家色，Go 端或建置期執行同一閘門；M02 商品編輯的顧客畫面預覽沿用此層。
DS-5
Office 高密度元件只在 MOD-02/03 需求成立後擴充表格、篩選、日期區間（React Aria）。

工具與流程的判斷

程式碼是唯一權威；Figma 為選用鏡像。理由：Linear 無設計稿、P-75 鎖定 MVP 範圍、目前沒有專職設計師；而 bridge 能繪製圖層，但不能建立或同步變數。若日後需要 Figma 審查，應建立獨立的 Tojima Figma 檔（目前 bridge 連著的是 Tachiko Sheet 檔，不可寫入本案內容），並先把本機 bridge 由 0.0.19 更新到已驗證的 0.0.22（才有 import_html_layers）。

本輪研究的工具分工：Claude（Opus）負責研究、決策與原型；Linear／Sheet 調查以平行子代理完成；提案由全新唯讀 Codex 審查。
